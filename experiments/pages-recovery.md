# GitHub Actionsの成果物と公開再実行

Math-Art-Lab PR #60の公開障害を出発点に、成功済みのジョブ出力が残る範囲と、別試行の成果物が同時に残る状況を検証する。採用方式は所有者判断に留保する。

## 比較

|観点|方式A 公式Action・2ジョブ|方式B 直接API・2ジョブ|方式C 公式Action・3ジョブ|
|---|---|---|---|
|通常時|Validate → PrepareとDeploy。公開ジョブで梱包後すぐ公開。|Aと同じジョブ数。RESTで照合したIDを直接送信。|Validate → Prepare Pages → Deploy。独立したランナー割当と初期化が1回増える。|
|障害時|公開入口未到達・検証済みZIP有効なら後続ジョブを再実行。新しい名前で梱包し直す。|Aと同じ単位。送信結果不明なら停止し、状態を照合する。|公開入口未到達・準備済みZIP有効ならDeployだけを再実行。Prepare失敗や準備済みZIP失効ならPrepareとDeployを実行。Validate成果物が失効した場合は全体が必要。|
|CI消費|通常と公開前失敗の再実行で短い後続ジョブ1つ。|ジョブ数はAと同じ。独自ポーリングの待ち時間が消費に影響。|通常は短いジョブ2つ。Deployだけの再実行は1つだが梱包・通信を省く。Privateの課金分はジョブごとに分へ切り上げ。|
|選択の安全性|一意な試行別名を照合する。Actionが内部APIで名前を再解決し、0件・複数なら停止。|公開時の名前再検索を省く。公開用成果物のIDを直接送信する。RESTの欠落時は停止し、検証済み成果物の取得は内部一覧に依存する。|Aと同じ名前解決。DeployはPrepareのID・名前・ダイジェストを受け取り、自分の試行番号から名前を再生成しない。|
|認証と権限|本番では公開ジョブにPages/OIDC。固定公式Actionがトークン取得、状態監視、既知IDの取消を処理。|本番のPages/OIDC権限は同等。トークン取得、POST、結果不明、監視、タイムアウト、取消を自前で扱う。|梱包のジョブには公開権限を付けず、Deployに限定できる。公式Actionの扱いと限界はAと同じ。|
|重複と応答喪失|公開入口に達した試行があれば自動再送を避ける。公式取消は既知IDが必要。|1回だけPOSTする設計。受理後に応答が失われると公開状態を照合するまで再送できない。|Prepare分離だけでは同一・別Runの公開重複を排除できない。Aと同じ履歴ゲートが必要。|
|保守|固定版更新と照合・再実行ゲートを保守。|API・認証・状態名・取消・監視・期限の仕様変更を追うコードが増える。|公式Actionを使いつつジョブ出力、別々の保持期限、部分再実行手順を追加で保守。|
|成果物管理|Validateと公開用は別ID。公開ジョブ再実行で新しい公開ZIPが追加される。|Aと同じ。送信IDを追跡しやすい。|Prepareだけが公開ZIPを作る。Deploy単独再実行は同じIDを使い、公開ZIPの件数が増えない。|
|横展開|既存Pages用ワークフローへ適用しやすい。|IDを渡せるAPIに応用できるが状態遷移はサービス固有。|梱包が重い、または公開権限を限定したい複数段階の配布にも転用しやすい。|
|実証上の制約|隔離環境では名前の内部可視性までを観察。公式deploy-pagesそのものの呼出しは本番と切り離した別承認の工程。|隔離環境ではID・履歴・停止まで。実OIDC、Pages受付・完了・取消は別承認の工程。|Prepare→Deployの出力継承と復旧時間を追加測定。実Pagesの制約はAと同じ。|

固定コードは [deploy-pagesの成果物照合とPOST](https://github.com/actions/deploy-pages/blob/368f82528645a54fb793d4d04e342629a3f51346/src/internal/api-client.js)、[監視と取消](https://github.com/actions/deploy-pages/blob/368f82528645a54fb793d4d04e342629a3f51346/src/internal/deployment.js)、[download-artifactのID取得](https://github.com/actions/download-artifact/blob/9000827ccba6bdab643e8b6fd33ac0654aef8333/src/download-artifact.ts)を参照。公開の[REST仕様](https://docs.github.com/en/rest/pages/pages)は成果物IDとOIDCトークンを受け取る。GitHubの[再実行仕様](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)は、再実行対象外のジョブの出力が引き継がれると明記。対応する実環境測定は保留。

## 測定値と判定

- 旧公式方式の成功対照 [Run 45825345359](https://github.com/tetsujisugimori-coder/Math-Art-Lab/actions/runs/45825345359) はValidate 34分37秒、後続開始まで4分21秒、後続ジョブ11秒、Validate開始から完了まで39分09秒。梱包・転送側の3ステップ合計2秒、公式公開ステップ6秒。A/B/Cの実測値として流用しない。
- [正式CI 45892367339](https://github.com/tetsujisugimori-coder/Math-Art-Lab/actions/runs/45892367339) はValidate 34分55秒、公開ジョブはスキップ。422単体、開発回帰588件成功・2件スキップ、公開ビルドスモーク448件成功。
- Work CloudのDebianで、成功対照の約298 KBの検証済みZIPを読み込み、CRCを検査しメモリ上で非圧縮tarを作る処理を31回測定。中央値3.84ms、範囲3.62〜5.78ms。ネットワーク、ランナー待ち、公開、課金は含まない。
- A/B/Cの通常時・障害時のGitHub上の実測はすべて `NOT_TESTED`。計測時はジョブ開始・終了時刻から待ち時間と実行時間を分け、比較用の内部一覧観測ステップは本番候補の時間から除外する。課金分数の比較は計算値と実際の利用明細を区別する。

## 実験手順

追加課金なしで使える枠が確認できたときだけ、対象Draft PRに `run-rerun-baseline` ラベルを1回付けて通常系のA/B/Cを初回だけ実行する。成功後に `run-rerun-experiment` ラベルを1回付け、下表の復旧系を実行する。対象ブランチからの同一リポジトリPRに限定する。最大2 Run、通常系1試行、復旧系6試行、各ジョブ2分、計40ランナー分以下、各Runの壁時計30分。上限に達したら停止し、欠落結果を記録する。

|試行|操作と期待結果|
|---|---|
|1|初回。ValidateとC Prepareが完了。A/B/Cの公開ジョブは公開代替処理の直前に意図的に失敗。|
|2|Aの後続ジョブだけを再実行。Validateの試行1 IDを再利用し、公開形ZIPは新規。|
|3|Bの後続ジョブだけを再実行。試行1のValidate IDと試行3の公開形ZIP IDを記録。|
|4|C Deployのみ再実行。C Prepareの試行1 IDを維持し、別のZIPを作成しない。|
|5|C Prepareを指定して再実行。C Deployも実行。公開形ZIP IDは新規。過去の模擬公開成功を検知して停止。|
|6|全ジョブを再実行。ValidateとPrepareのIDは新規。過去の模擬公開成功を検知して停止。|

全試行でRun IDとattempt、ジョブ・ステップ履歴、RESTとdownload-artifactの内部一覧ログのID集合、名前解決とID取得、旧成果物存続を照合する。予定外の失敗、APIの欠落・曖昧な履歴、ページング、既知IDとRESTの不一致が起きたら続行せず、ログと検出位置を記録する。成果物の欠落・重複・誤ID・失効・ダイジェスト欠落と不一致、一覧の件数不一致とID重複の8ケースは合成検査を行う。

この実験が模擬するのは成果物の同一性、履歴、安全停止。Math-Art-Labの既存公開条件、サービス側の認証、受付、公開完了、取消、応答喪失は実証対象外。A/Cはdownload-artifactの内部APIで名前取得を観察するため、deploy-pagesが行う名前フィルターの厳密な可視性は別途確認が必要。BはIDをログに渡すだけでネットワーク送信を行わない。

## 保留事項

初回0件の根因、別Runでの重複防止、main確認直後の競合、実deploy-pages内部可視性、受付後の応答喪失、過去履歴欠落による過剰停止、既存成果物名を前提にした外部手順を研究対象にする。次回は実際の待ち時間と復旧時の省略効果を測定し、方式の選択は所有者に委ねる。
